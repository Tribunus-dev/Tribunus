# ADR 0041: Tribunus Server UX

## Status
Proposed — June 2026

## Context

The Tribunus server currently provides the core inference functionality but the user experience is clunky — scattered configuration, opaque errors, no model management, no progress indicators. For a desktop-first inference engine competing with Ollama, LM Studio, and llama.cpp, the UX is the product.

## Decision

### Single-Command Bootstrap

`tribunus run <model-name>` downloads, compiles, loads, and serves in a single command (Ollama pattern). If the model is not found locally, search known catalogs (HuggingFace, GGUF registry). Progress bars during download and compilation. Model is automatically available at localhost:8080 when ready.

### Status Dashboard

`tribunus ps` shows loaded models, active requests, VRAM usage, backend, uptime. `--watch` flag for live dashboard (refresh every 1s with terminal UI). Columns: model name, backend, VRAM used/total, active requests, uptime, temperature.

`GET /health` returns full runtime state instead of a static `{"ok": true}`:
```json
{
  "model": "Qwen3-0.6B",
  "backend": "mlx-metal",
  "uptime_seconds": 3600,
  "active_requests": 3,
  "vram_used_gb": 4.2,
  "vram_total_gb": 8.0,
  "temperature_celsius": 65.0,
  "phase": "decode",
  "tokens_generated": 1024,
  "tokens_per_second": 35
}
```

### Diagnostics

`tribunus doctor` checks: GPU drivers (vulkaninfo, nvidia-smi, rocm-smi, zeDeviceGet), model compatibility, disk space for model cache, thermal throttling.

`tribunus estimate <model>` before downloading: estimate VRAM needs, recommend quantization level (Q4 vs Q8 vs fp16), warn if model won't fit available VRAM.

### Compute Image Awareness

`tribunus show <model>` displays the compute image contents: which backends are targeted, per-phase evidence (latency, GFLOPS), arena plan (page counts, ring sizes), receipt from last compilation. This is Tribunus's unique differentiator — users can see WHY their model performs the way it does.

### Configuration

Single `tribunus.jsonc` file with schema validation on startup. Clear priority: CLI flags > environment variables > config file > defaults. Effective config printed on startup with `--verbose`.

Human-friendly Caddy-style format (JSONC with comments). Auto-generated by `tribunus init`.

### API Design

OpenAI-compatible API (`/v1/chat/completions`, `/v1/models`) plus Tribunus-specific management endpoints:
- `GET /v1/models` — list loaded models with compute image evidence
- `POST /v1/models/load` — load a model
- `DELETE /v1/models/{name}` — unload a model
- `GET /v1/receipts?since=<timestamp>` — stream or poll receipts

Swagger at `/docs`, playground at `/playground` (like Swagger UI for chat completions).

### CLI Ergonomics

Positional arguments: `tribunus run <model>`, `tribunus show <model>`, `tribunus estimate <model>`. Colored output by default, `--json` flag on all informational commands. Tab-completion for bash/zsh/fish. Progress bars during download and compilation (sparkline-style for terminal).

### Error UX

Every error includes a "fix" hint:
- Model not found: suggest similar models from catalog
- VRAM full: suggest `tribunus estimate` with lower quantization, or unload another model
- Backend missing: show install command (`brew install mesa-vulkan-drivers`)
- GPU not found: list detected GPUs, explain why the desired one isn't available
- Compilation failed: show the phase that failed and the error reason from the realizer taxonomy (ADR 0037)

## Consequences

**Positive:** Builds on proven patterns from Ollama, LM Studio, and Caddy. Key differentiator: compute-image awareness gives users visibility into model performance. Errors are actionable.

**Negative:** CLI/API/console is a large surface to polish. Model catalog integration requires maintaining a model registry.

**Effort:** 3-4 weeks for CLI + API + status dashboard. 1-2 weeks for model catalog integration.

# Dataset Card for Tribunus Compute Evidence Corpus

**tl;dr:** This dataset contains reproducibility evidence and benchmark observations from Tribunus Compute. It is not a general LLM training corpus. It is intended for systems research on local inference execution, compiler placement, backend qualification, and reproducible benchmark methodology.

## Table Structure

The evidence corpus consists of five canonical tables. They are related through shared identifiers enabling precise traceability from hardware configuration through to compiled execution artifacts.

### `runs`
The central orchestration table. Each row corresponds to one benchmark execution — a single model, quantization, backend, and hardware combination producing a set of timing and memory observations. Key columns: `run_id` (primary key), `model_id`, `quantization`, `backend`, `hardware_id`, `num_tokens`, `tokens_per_second`, `ttft_ms`, `peak_memory_mb`, `test_date`, `tribunus_commit`, `repo_dirty`, `schema_version`, `dataset_release`. Every other table references a specific `run_id`.

### `hardware_profiles`
Describes the physical hardware on which a run was executed. Joined to `runs` on `hardware_id`. Contains `soc_name` (e.g., Apple M2 Max), `cpu_core_count`, `gpu_core_count`, `ne_engine_count`, `ram_gb`, `os_version`, `thermal_mode`, `sysctl_flags`. Multiple runs may share the same hardware profile when executed on the same machine under equivalent conditions.

### `backend_observations`
Per-backend execution metrics collected during a run. Joined to `runs` on `run_id` and keyed by `(run_id, backend)` — a single run may test multiple backends sequentially. Contains `backend` (mlx, coreml, accelerate, bnns), `tokens_per_second`, `ttft_ms`, `peak_memory_mb`, `warmup_tokens`, `temperature`, `decoding_strategy`, `measurement_clock`, `num_repetitions`, `aggregation_method`.

### `compiler_manifests`
Diagnostics and metadata from the compilation step that produced the executable backend artifact. Joined to `runs` on `run_id`. Contains `compiler` (mlx, coremltools, etc.), `compiler_version`, `compilation_time_ms`, `optimization_flags`, `deployment_target`, `compile_status`, and a free-form `diagnostics` JSON field for warnings, errors, and heuristics.

### `artifacts`
References to compiled model artifacts on disk or in object storage. Joined to `runs` on `run_id`. Each row represents one artifact file with `artifact_path`, `artifact_sha256`, `artifact_size_bytes`, `format` (mlmodelc, mlpackage, mlx, etc.), `compression`, and `created_at`. Multiple artifacts may belong to a single run (e.g., a Core ML model and its companion metadata).

## Data Provenance

Every row in the evidence corpus carries the following provenance fields: `run_id` (UUID v4), `schema_version` (semantic version of the table schema at time of insertion), `dataset_release` (release tag of the published corpus snapshot), `tribunus_commit` (Git SHA of the Tribunus compute kernel that generated the data), and `artifact_sha256` (SHA-256 digest of the primary output artifact). Data is generated by the Tribunus compute kernel running on Apple Silicon hardware across M1, M2, M3, and M4 families. The evidence corpus is the raw, unfiltered output of the automated benchmark harness.

## Methodology

- **Hardware:** Apple Silicon Macs (detailed in the `hardware_profiles` table), covering M1 through M4 generations in various core configurations
- **Backends:** MLX (Apple MLX framework), Core ML (Apple CoreML), Accelerate (Apple BLAS/LAPACK), BNNS (Apple Basic Neural Network Subroutines)
- **Quantization methods:** `mlx-q4_0`, `mlx-q8_0`, `fp16`, `fp32` — bit widths and schemes vary by backend
- **Warmup policy:** 3 warmup tokens before measurement begins, to prime caches and pipeline state
- **Token sampling:** Greedy decoding with temperature=0 for deterministic, reproducible outputs
- **Measurement clock:** `mach_continuous_time` on macOS / `clock_gettime(CLOCK_MONOTONIC)` on Linux; all intervals reported in milliseconds with microsecond precision
- **Repetition:** Minimum 3 independent runs per configuration; additional runs scheduled when coefficient of variation exceeds thresholds
- **Aggregation:** Median of runs reported as the central estimate; min and max included for dispersion; no outlier removal

## Limitations

- **Hardware coverage:** Early measurements are Apple Silicon-heavy (M1-M3 families). Coverage of M4 and Pro/Max/Ultra variants is ongoing
- **Generalizability:** Results may not generalize to NVIDIA, AMD, or datacenter-class systems — the dataset is deliberately scoped to Apple Silicon inference
- **Experimental branches:** Some rows reflect experimental Tribunus branches where `repo_dirty = true`. These are included for completeness but may exhibit non-representative performance
- **Thermal throttling:** Thermal state is not always controlled in early releases. Check the `thermal_mode` column in `hardware_profiles` and filter outliers when thermal_mode is non-nominal
- **Compiler diagnostics:** Compiler warnings, heuristics, and optimization decisions are collected in `compiler_manifests.diagnostics` but not yet curated or normalized across compiler versions
